Payments API · Ruby on Rails

A payments engine that lives outside the app

Problem
Organisations need to initiate payments, manage them and issue refunds — without payment logic spreading through the host application.
Approach
Payment handling lives in a mountable Rails Engine, with a Facade keeping business logic out of the controllers.
Outcome
One payment module that can move between projects without duplicated code, while the host app stays thin.
Engineering details
  • REST endpoints to initiate and manage payments and to process refunds
  • The engine is isolated from the main app, so it can be versioned and reused on its own
  • A Facade layer separates domain logic from HTTP concerns
  • Built test-first with RSpec and FactoryBot on PostgreSQL

Real-time AI chat that never blocks

Approach

Distributed systems · Java

Message-driven microservices, built test-first

Problem
Services that only talk through a message broker are hard to reason about — and to test — as one system.
Approach
Stand-alone Quarkus services communicate over RabbitMQ, and Cucumber scenarios describe the behaviour before it is implemented.
Outcome
Behaviour is specified as executable scenarios, and the full system runs locally through Docker Compose.
Engineering details
  • Each service is independent and handles its own web requests with Quarkus
  • Inter-service communication goes through RabbitMQ
  • Facade, Adapter and Singleton patterns keep boundaries explicit
  • Every service is containerised with Docker; Docker Compose runs the whole system

Systems · UML

Toll road management system

A complete UML model built by a project team in DTU’s System Integration course (02291) and awarded the top grade. Six views, each answering a different question about the same system.

Views 4–6 follow one requirement, Update toll rate, from interaction to constraint to acceptance test. Those three are my own work.

Component diagram

What are the parts, and how do they connect?

Three tiers — toll-lane hardware, station servers and the enterprise backend — that only talk through declared ports and interfaces.

Component diagram — Architecture

Class diagram

What does a lane computer own and expose?

The TollLaneComputer’s operations, one interface per device port, and the report structures it sends upstream.

Class diagram — Structure

State machine

How does the server react to events?

From idle, the server handles ticket checkout, tag checkout and tag validation — and always returns to idle with a definite answer.

State machine — Behaviour

Sequence diagram · Update toll rate

How does a rate change travel through the system?

A manager enters a new rate. The enterprise server validates it, then either returns an error or pushes it to every station server and confirms.

Sequence diagram — Interactions

OCL · Update toll rate

What must always be true?

A rate is never negative, every station must be running before an update, and afterwards every station holds the new rate.

OCL — Constraints

Acceptance tests · Update toll rate

How do we know it works?

Fixture tables cover the main scenario and both failure paths: a station server offline, and an invalid negative rate.

Acceptance tests — Validation

The habit carries into everyday work: agree on interfaces first, write the invariants down, and define acceptance criteria before the implementation starts.

Operating AI systems

Treat AI features like any other production code: track token usage, latency and output quality, automate health checks and benchmarks, and change prompts or retrieval only against a measured baseline.

  • Observability
  • Cost monitoring
  • Health checks
  • Evaluation
Nine principles I apply to production AI
Minimise LLM calls
Use deterministic logic where a model adds nothing; reserve calls for real language understanding or generation.
Treat prompts as code
Design, test and refine them. A well-engineered prompt beats a bigger model with a vague one.
Cache reusable context
Don’t resend static context. Persist decisions in memory files and load only what the task needs.
Right model for the task
Capable models where quality matters; smaller, faster ones for routing, classification and low-stakes output.
Fix retrieval first
Better context beats a larger model reading poor context.
Balance latency, quality and cost
Design for all three from the start, not as an afterthought.
Measure continuously
Track tokens, latency and quality in production so degradation is caught before users notice.
Extract reusable workflows
A pattern used twice is worth extracting; used ten times, it becomes infrastructure.
Design for observability
AI systems fail quietly. Instrument outputs and monitor drift so the system stays trustworthy.
